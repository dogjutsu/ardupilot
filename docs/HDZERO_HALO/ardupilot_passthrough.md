ArduPilot Passthrough Implementation: A Hardware Definition (hwdef.dat) Developer's GuideExecutive SummaryThis report provides a comprehensive technical guide for ArduPilot hardware developers on the correct implementation of two distinct "passthrough" functionalities within the hwdef.dat hardware definition file. These features are critical for modern peripheral configuration but require precise hardware-level definitions.Serial Passthrough: A software feature that bridges the autopilot's USB port (logical SERIAL0) to a physical UART (e.g., SERIAL2). This allows a user's PC to directly configure serial devices such as ELRS receivers, GPS modules, or telemetry radios.1ESC Passthrough: A protocol-level feature that tunnels ESC configuration commands (e.g., for BLHeli_32, AM32) from a PC, through the autopilot's USB, and over the DShot motor-control signal lines.3This document details the specific hwdef.dat definitions required for the USB controller, logical port mapping, DMA-enabled serial ports, and timer-based motor outputs that are foundational to these features. It analyzes common failure modes and establishes best-practice design patterns for new flight controller hardware definitions.1. Core USB Hardware Definitions (hwdef.dat)The foundation for all USB-based functionality, including passthrough, begins with the correct definition of the microcontroller's (MCU) USB On-The-Go (OTG) peripheral.1.1. USB Data Pin DeclarationThe primary USB connection requires defining the D- (OTG_FS_DM) and D+ (OTG_FS_DP) pins and associating them with the MCU's OTG1 (Full-Speed) or OTG2 (High-Speed) peripheral.A typical declaration in hwdef.dat for an STM32-based MCU is:PA11 OTG_FS_DM OTG1
PA12 OTG_FS_DP OTG1
(Source: 5)These lines map the physical MCU pins PA11 and PA12 to the first USB peripheral, OTG1. This OTG1 identifier is then used in the SERIAL_ORDER definition to create a logical serial port.1.2. VBUS Sensing and Hardware "Gotchas"A common point of failure when porting new hardware is the USB VBUS (Voltage BUS) sensing mechanism.VBUS Pin Definition: Many boards include a pin (e.g., PA9) that detects the 5V power from a connected USB cable. This allows the ArduPilot bootloader and firmware to know when a USB host is physically present.5PA9 VBUS INPUT OPENDRAIN
(Source: 5)Failure Mode: If a board design omits this VBUS sensing pin, the ArduPilot firmware will boot but may never initialize the USB stack, as it is perpetually waiting for a VBUS "high" signal that will never come. The symptom is a "dead" USB port where no COM device appears in the host PC's device manager.6hwdef.dat Solution: For boards lacking VBUS hardware, the hwdef.dat file must include directives to bypass the VBUS check and force the USB peripheral to initialize.define HAL_USE_USB_VBUS_SENSE 0
define HAL_USB_FORCE 1
(Source: 8)HAL_USE_USB_VBUS_SENSE 0 disables the VBUS sense logic, and HAL_USB_FORCE 1 compels the OTG stack to start regardless of pin state. This is mandatory for reliable USB operation on such hardware.2. Logical USB Port Assignment (SERIAL_ORDER)The hwdef.dat file maps physical peripherals (like OTG1 and USART2) to logical SERIALx ports that the user interacts with. This is controlled by the SERIAL_ORDER directive.2.1. Standard USB Mapping (SERIAL0)The ArduPilot HAL defines up to 8 logical serial ports (SERIAL0 to SERIAL7).9 By convention, SERIAL0 is always the primary USB port.9 This mapping is established by placing OTG1 as the first item in the SERIAL_ORDER list.Example hwdef.dat entry:# Logical: SERIAL0,  SERIAL1,  SERIAL2,  SERIAL3
SERIAL_ORDER OTG1 USART2 UART4 USART3
(Source: 5)In this example, the OTG1 peripheral is mapped to SERIAL0, USART2 is mapped to SERIAL1, UART4 to SERIAL2, and so on. The user will then see SERIAL0 in their ground station as the "USB" port, typically configured for MAVLink2 protocol by default.102.2. Composite USB Devices (OTG1 and OTG2)More advanced MCUs (e.g., STM32H7, F7) support multiple USB peripherals, commonly OTG1 and OTG2. When both are defined in SERIAL_ORDER, ArduPilot creates a "Composite USB Device".11This composite functionality is distinct from "Serial Passthrough." It does not bridge ports; rather, it presents two independent serial ports to the host PC over the single USB cable.11hwdef.dat Definition:# Logical:  SERIAL0, SERIAL1, SERIAL2, SERIAL3, SERIAL4, SERIAL5, SERIAL6
SERIAL_ORDER OTG1 USART2 USART3 UART4 UART8 UART7 OTG2
(Source: 12)Logical Mapping:OTG1 maps to SERIAL0.11OTG2 maps to the highest available logical port (in this case, SERIAL6).11Typical Use Case: This is most commonly used to provide simultaneous MAVLink and DroneCAN access.11 The defaults.parm file will set SERIAL0_PROTOCOL = 2 (MAVLink2) and SERIAL6_PROTOCOL = 22 (SLCAN).11 The developer must ensure the board uses a composite-capable USB VID/PID pair.113. Implementing Serial Passthrough (e.g., for ELRS Receivers)Serial Passthrough is a software function that routes all data from a "source" port (like SERIAL0) to a "destination" port (like SERIAL2), effectively making the autopilot invisible and allowing direct PC access to the peripheral.13.1. User-Facing ParametersThe feature is enabled by the user via the following parameters 1:SERIAL_PASS1: The source port. Defaults to 0 (USB), which is correct for this use case.SERIAL_PASS2: The destination port, corresponding to the logical SERIALx number of the physical UART (e.g., "2" for SERIAL2).SERIAL_PASSTIMO: A timeout in seconds (e.g., 60) after which passthrough reverts. A value of 0 disables the timeout.1SERIALx_BAUD: The baud rate of the destination port (e.g., SERIAL2_BAUD) must be set to match the target device (e.g., 230400 for a GPS, or 420000 for ELRS).13.2. hwdef Physical UART DefinitionFor SERIAL_PASS2 to function, a physical UART must be defined in hwdef.dat and mapped via SERIAL_ORDER. For example, to define USART2 and map it to SERIAL1 (as seen in 5):# telem1

Critical Requirement: DMA for High-Speed ProtocolsThe most significant hwdef consideration for serial passthrough is the peripheral's data rate. Modern RC protocols like ELRS (ExpressLRS) and CRSF (Crossfire) operate at very high baud rates (420kbaud and 416kbaud, respectively).15The Problem with Polling: At baud rates exceeding approximately 200kbaud, standard, CPU-driven "polling" of the UART buffer becomes unreliable.17 On heavily loaded MCUs (especially F4-class), the CPU cannot service the UART receive (RX) buffer "evenly," leading to buffer overruns, dropped packets, and link failure.17The Solution: DMA (Direct Memory Access): DMA offloads this task from the CPU. It allows the MCU's DMA controller to move data from the UART peripheral's RX buffer directly into memory, guaranteeing "even" and reliable data ingestion regardless of CPU load.17hwdef.dat DMA Syntax:To request DMA for a peripheral, simply omit the NODMA modifier.19To force no DMA (e.g., for a low-speed port or to resolve a resource conflict), add the NODMA modifier.5Mandatory DMA:# Good: USART2_RX is assigned to SERIAL1, DMA is requested
PD6 USART2_RX USART2
SERIAL_ORDER OTG1 USART2
No DMA:# Bad: USART2_RX is assigned to SERIAL1, but DMA is explicitly forbidden
PD6 USART2_RX USART2 NODMA
SERIAL_ORDER OTG1 USART2
The "Dark Art" of DMA Allocation: DMA channels are a finite, shared resource on the MCU, contended for by UARTs, SPI, I2C, and Timers (for DShot).18 A developer requesting DMA (by omitting NODMA) is not guaranteed to receive it. The ChibiOS HAL build scripts (chibios_hwdef.py) 20 attempt to arbitrate these requests.The hwdef author must verify the allocation. After compiling the firmware, the developer must inspect the generated build/<boardname>/hwdef.h file 17 to confirm that the intended high-speed UART (e.g., HAL_UART_B corresponding to USART2) was successfully assigned a DMA stream. If a conflict prevents allocation, the developer must re-architect the hwdef.dat, perhaps by moving a lower-priority peripheral (like a VTX) to a NODMA port, to free up the DMA channel for the critical RC-input UART. Implementing ESC Passthrough (for BLHeli_32/AM32)This second passthrough type is functionally different. It does not use the ArduPilot serial port mapping. Instead, it tunnels configuration data from the PC (via USB) to the motor outputs, communicating with the ESCs using the DShot protocol.44.1. User-Facing ParametersThe feature is enabled by the user with these parameters:SERVO_BLH_AUTO = 1: Automatically enables passthrough on all outputs configured as motors (SERVOx_FUNCTION > 0).4SERVO_BLH_MASK: For non-multirotor frames (e.g., planes), this bitmap manually selects which outputs (channels) should be enabled for passthrough.24SERVO_BLH_OTYPE: Must be set to a DShot protocol (e.g., 4 for DShot150, 5 for DShot300, 6 for DShot600).234.2. hwdef Requirements for Motor OutputsFor ESC passthrough to function, the motor outputs must be defined as DShot-capable PWM outputs. This requires assigning a physical pin to a hardware Timer (TIM) peripheral.Example hwdef.dat motor definitions:PE14 TIM1_CH4 TIM1 PWM(1) GPIO(50) BIDIR
PE13 TIM1_CH3 TIM1 PWM(2) GPIO(51)
PE11 TIM1_CH2 TIM1 PWM(3) GPIO(52) BIDIR
PE9 TIM1_CH1 TIM1 PWM(4) GPIO(53)
(Source: 27)PE14: The physical MCU pin.TIM1_CH4: The specific hardware timer (Timer 1) and channel (Channel 4) for this pin.TIM1: The timer group (see Section 4.4).PWM(1): The logical ArduPilot output number. This pin will be controlled by SERVO1_... parameters.BIDIR: The critical modifier for modern ESC features.4.3. Critical Requirement: The BIDIR ModifierThe BIDIR modifier is mandatory for enabling Bi-directional DShot (bdshot).26 bdshot is the protocol that allows an ESC to send telemetry (RPM, temperature, voltage) back to the autopilot over the single motor signal wire.4 This RPM data is essential for advanced features like the harmonic notch filter.The ESC passthrough mechanism relies on this same bi-directional hardware capability. A hwdef file that omits the BIDIR tag on a motor output may fail to perform ESC passthrough or bi-directional DShot on that specific channel.A common failure mode is seen where a user flashes bdshot firmware, but the passthrough configurator fails to detect one or more ESCs.32 Analysis of the corresponding hwdef.dat often reveals that the non-functional motor's pin definition lacks the BIDIR tag, while the working motors' pins have it.32This BIDIR definition is a low-level, compile-time hardware-timer-DMA allocation. It cannot be remapped by the user via parameters. If an output lacks the BIDIR tag in the hwdef, the only solution is for the user to re-solder the motor to a BIDIR-capable pin or for the hwdef author to correct the file.324.4. Critical Requirement: Timer Grouping ConstraintsA fundamental rule of the ArduPilot HAL is that all outputs on the same timer group must run the same protocol.25In the example from Section 4.2, outputs PWM(1) through PWM(4) are all on the TIM1 group.27 This means they must all be DShot, or all be standard PWM. It is impossible to run DShot on PWM(1) and PWM on PWM(2).This is a critical constraint for board design and hwdef definition.Good Design: A hwdef that places all primary motor outputs (e.g., 1-8) on dedicated timer groups (e.g., TIM1, TIM8) and all servo outputs (e.g., 9-12) on different timer groups (e.g., TIM2, TIM3). This allows the user to run DShot on motors and PWM on servos.Bad Design: A hwdef that mixes motors and servos on the same timer group. This creates "high maintenance" boards 33 that force users into compromises (e.g., running DShot on a servo, or being unable to use bdshot on their motors).4.5. The IOMCU Co-Processor ExceptionBoards with an IOMCU (I/O Microcontroller), such as the Pixhawk and Cube families, handle DShot and passthrough differently.23 The "MAIN" outputs on these boards are controlled by a separate co-processor, not the main FMU (Flight Management Unit).To enable DShot and passthrough on these outputs, the hwdef.dat for the main FMU must include the DShot-capable IOMCU firmware in its own flash, using the ROMFS (ROM File System) directive.34Example hwdef.dat entry for a CubeOrange:ROMFS io_firmware_dshot.bin Tools/IO_Firmware/iofirmware_f103_dshot_lowpolh.bin
define HAL_WITH_IO_MCU_BIDIR_DSHOT 1
(Source: 34)This allows the user to set BRD_IO_DSHOT = 1, which instructs the main FMU to flash this io_firmware_dshot.bin file to the IOMCU on the next boot, thereby enabling DShot capabilities on the IOMCU-controlled outputs.235. Analysis and hwdef Design RecommendationsBased on the technical requirements, the following best practices and failure-mode analyses are provided for hwdef developers.5.1. Summary of Common Passthrough Failure Modes and DiagnosticsFailure 1: USB Port Not Detected After Flashing.Symptom: Board is flashed (e.g., via DFU), but no USB COM port appears for the bootloader or main firmware.6Root Cause: The board hardware lacks VBUS voltage sensing, and the hwdef has not been configured to compensate.6hwdef Fix: Add define HAL_USE_USB_VBUS_SENSE 0 and define HAL_USB_FORCE 1 to the hwdef.dat file.8Failure 2: Unreliable ELRS/CRSF RC Link (High Packet Loss).Symptom: RC link is sporadic, GCS shows high packet loss, or MAVLink "mode change" spam occurs.15Root Cause: The ELRS/CRSF receiver is connected to a non-DMA (polled) UART that cannot reliably process the 420kbaud data rate.16hwdef Fix: The developer must identify a DMA-capable UART, ensure it is defined without the NODMA tag, and verify its DMA allocation in the compiled hwdef.h.17 The board's documentation must instruct the user to connect the receiver to this specific port.22Failure 3: SERVO_BLH_BDMASK Parameter is Missing.Symptom: User cannot enable bi-directional DShot; the SERVO_BLH_BDMASK parameter does not appear in the parameter list.33Root Cause: The firmware build flashed to the board is not a bdshot target, indicating the base hwdef does not support it.33hwdef Fix: The developer must add the BIDIR tag to the motor output definitions (see below).28Failure 4: ESC Passthrough Fails on Some Motors.Symptom: BLHeliSuite connects but only detects 3 of 4 ESCs.32Root Cause: The firmware is bdshot-capable, but the non-working motor is connected to a pin that lacks the BIDIR tag in the hwdef.dat.32hwdef Fix: Add the BIDIR tag to all motor output PWM() definitions in the hwdef.dat.Failure 5: AM32/BLHeli Passthrough is Unreliable.Symptom: Flashing the ESC firmware fails randomly, often around 50% 36, or the configurator reports "No Response from ESC" on the first try.37Root Cause: This appears to be a software timing issue in the ArduPilot passthrough implementation, not a hwdef error.36hwdef Fix: No hwdef fix is available. The developer should be aware that testing may require multiple connection attempts.375.2. Best Practices for hwdef Design and DocumentationThe hwdef file and its corresponding Readme.md documentation are inseparable.22Strategic UART Assignment: Do not assign physical UARTs to logical SERIALx ports randomly. Identify the 1-2 physical UARTs with the best DMA capabilities. In the Readme.md file, create the mandatory "UART Mapping" table.22 This table must include a "Notes" column that explicitly states "DMA Enabled" for these high-speed ports.22 This guides the user to connect their ELRS/CRSF receiver to the correct physical port, preventing link failures.Future-Proof Motor Outputs: The best practice is to define all primary motor outputs (e.g., 1-8) with the BIDIR tag, assuming the hardware pins are capable.27 This makes the main firmware target bdshot-capable by default and eliminates the need for separate, confusing bdshot firmware variants 28, thus reducing maintenance and user error.Mandatory Documentation: The hwdef developer is responsible for creating the Readme.md file.22 This file must clearly document:UART Mapping: A table listing the Serial#, Protocol, Port (physical UART), and Notes (e.g., "DMA Enabled").22PWM Output: A table listing the outputs and their Timer Groups, explicitly stating the DShot/bdshot capability.22RC Input: Specific instructions for bi-directional protocols like CRSF/ELRS, pointing them to the correct DMA-enabled UART.225.3.
